# AI-Powered After-Call Automation Platform

Exology Pioneer Program — Final Project

An end-to-end pipeline that turns a raw customer-service call transcript into a
grounded CRM documentation record, a deterministic routing decision, and a
persisted, evaluated, dashboarded result — with no step trusting the LLM for
anything beyond text generation.

```
Transcript
    │
    ▼
 intake.py            → load & validate the transcript
    │
    ▼
 customer_lookup.py    → resolve the customer record
    │
    ▼
 handbook_search.py    → RAG retrieval from the documentation handbook
    │
    ▼
 documentation_engine.py → Gemini generates ONE grounded DocumentationRecord
    │
    ▼
 business_rules.py     → pure Python decides AUTO_SAVE / HUMAN_REVIEW /
    │                     ESCALATE / NON_INTERACTION (never the LLM)
    ▼
 review.py             → routes the record to its queue (deterministic)
    │
    ▼
 storage.py            → persists one JSON file under outputs/
    │
    ▼
 evaluation.py         → scores outputs/ against data/answer_key.json
    │
    ▼
 dashboard.py          → charts + summary reports from outputs/
```

`main.py` orchestrates the first six stages end to end for a single
transcript. `evaluation.py` and `dashboard.py` operate independently,
afterward, over whatever has already been persisted to `outputs/`.

## Architecture principles

- **Single Responsibility per module.** Each file in `app/` does exactly one
  job (see table below) and is forbidden — by its own docstring and by
  construction — from doing any other module's job.
- **The LLM never decides anything.** `documentation_engine.py` is the only
  module that calls Gemini, and it only *generates* a documentation draft.
  `business_rules.py` is pure, deterministic Python and is the sole authority
  on routing; the model's `escalation_recommended` flag is a *recommendation*,
  never a decision.
- **Strict grounding.** Every field the model cannot support with the
  transcript, the customer record, or retrieved handbook context comes back
  as `"Not stated"` rather than being invented.
- **Swappable persistence.** `storage.py` exposes `save_record` /
  `load_record` / `list_records` / `delete_record` as the only contract the
  rest of the app depends on — the JSON-file implementation can be replaced
  with a real database without touching any other module.
- **Evaluation and dashboarding are pipeline-agnostic.** Both only read plain
  JSON from `outputs/`; neither imports the AI/business-logic modules, so
  either can be pointed at output from a different model entirely.

## Module reference

| Module | Responsibility |
|---|---|
| `app/intake.py` | Load, validate, and structure a raw transcript file. |
| `app/customer_lookup.py` | Look up a `Customer` by ID from `data/customers.json`, cached in memory. |
| `app/handbook_search.py` | RAG retrieval: chunk the handbook, embed with Gemini, persist a Chroma vector store, return the Top-K relevant rules. |
| `app/documentation_engine.py` | Call Gemini with strict grounding instructions; validate and return one `DocumentationRecord`. |
| `app/business_rules.py` | Deterministically evaluate a `DocumentationRecord` into a `BusinessDecision` (10 rules: grounding, sensitive content, escalation, confidence threshold, etc). |
| `app/review.py` | Route a `(DocumentationRecord, BusinessDecision)` pair to its queue and produce a `ReviewResult`. No side effects. |
| `app/storage.py` | Persist/read/list/delete `ReviewResult` records as JSON under `outputs/{records,reviews,escalations,archive}/`. |
| `app/main.py` | Orchestrates intake → customer_lookup → handbook_search → documentation_engine → business_rules for one transcript. Stops at the first failed stage. |
| `app/evaluation.py` | Compares everything in `outputs/` against `data/answer_key.json`; writes `outputs/evaluation/evaluation_report.{json,md}`. |
| `app/dashboard.py` | Reads `outputs/` + the evaluation report; computes distributions/statistics, renders matplotlib charts, exports `outputs/dashboard/`. |

## Setup

**1. Clone and create a virtual environment**

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
```

**2. Install dependencies**

```bash
pip install -r requirements.txt
```

**3. Configure your API key**

```bash
cp .env.example .env
# then edit .env and set GOOGLE_API_KEY=<your key>
```

Get a key at https://aistudio.google.com/apikey. `documentation_engine.py`
and `handbook_search.py` both read `GOOGLE_API_KEY` from the environment.

**4. Provide the data files**

- `data/customers.json` — a JSON array of customer records (must include
  `customer_id`).
- `data/handbook/*.md` — the documentation handbook, one topic per file.
- `data/transcripts/K-XXX.txt` — call transcripts. Each should include
  `Call ID:`, `Customer ID:`, and `Timestamp:` header lines so `intake.py`
  can extract them (any missing field is left as `None`, never guessed).
- `data/answer_key.json` — ground truth for `evaluation.py`, a JSON array of
  objects each with a `call_id` plus the fields listed below.

Answer key entry shape:

```json
{
  "call_id": "K-001",
  "summary": "...",
  "category": "Billing",
  "subcategory": "Refund",
  "priority": "Low",
  "disposition": "Resolved",
  "sentiment": "Neutral",
  "escalation_recommended": false,
  "decision": "AUTO_SAVE"
}
```

`decision` must be one of the four values `business_rules.py` can actually
produce: `AUTO_SAVE`, `HUMAN_REVIEW`, `ESCALATE`, `NON_INTERACTION`. An
answer-key entry using any other label (e.g. a `ROUTE_TO_REVIEW` typo) will
always be scored as a mismatch, since the pipeline can never produce it.

## Running the pipeline

**Process one transcript** (writes to `outputs/{records,reviews,escalations,archive}/`):

```bash
python -m app.main data/transcripts/K-001.txt
# or, using the configured default transcript:
python -m app.main
```

**Process every transcript you have** (PowerShell):

```powershell
foreach ($i in 1..27) {
    $id = "K-{0:D3}" -f $i
    python -m app.main "data\transcripts\$id.txt"
}
```

**Evaluate against the answer key** (writes `outputs/evaluation/`):

```bash
python -m app.evaluation
```

**Generate the dashboard** (writes `outputs/dashboard/`, including PNG charts):

```bash
python -m app.dashboard
```

Run all three in sequence to go from raw transcripts to a scored,
visualized result.

## Running the tests

```bash
pytest tests/ -v
```

The suite (100+ tests across all ten modules) uses fakes/mocks for every
external dependency — no real Gemini calls, no network — except the
`evaluation.py` and `dashboard.py` integration tests, which build **real**
`DocumentationRecord` → `BusinessDecision` → `ReviewResult` objects and run
them through the real `storage.py` to catch schema-mismatch bugs that
flat mock dictionaries can't.

## Known notes

- `google.generativeai` (used by `documentation_engine.py`) is Google's
  now-deprecated SDK; a `FutureWarning` on import is expected and harmless.
  A future migration to `google.genai` would only touch that one module.
- Gemini model names change over time. If you see a `404 NOT_FOUND` for a
  model, check `DEFAULT_MODEL_NAME` in `documentation_engine.py` and
  `_DEFAULT_EMBEDDING_MODEL` in `handbook_search.py` against Google's current
  model list.
- `data/vector_db/` and `outputs/` are regenerated by the pipeline and are
  git-ignored; delete `data/vector_db/` if you change the handbook contents
  and want it re-embedded from scratch.
